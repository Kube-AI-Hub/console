# 全站 E2E 基线复核（2026-11-16，部分完成）

> 对应能力矩阵 CHECK-02「全仓显式类型、构建、共享回归、全站 E2E」。
> 本记录只写实际跑过的命令与观察，不把并发结果当成判定。

## 1. 本批想回答的问题

1. 全站串行 E2E 在当前环境能否作为一次判定跑完？
2. `-n 4` 并发跑能否用于快速反馈？它的失败是否可信？
3. 本轮之前各批次的模块在合并后是否仍然通过？

## 2. 实际命令与观察

| 命令 | 结果 |
| --- | --- |
| `pytest tests/kube-frontend -m ui -q -p no:cacheprovider -n 0`（全站串行，376 个用例文件） | **未跑完**：18 分钟到达 18%，按此速率约需 95–110 分钟。为避免占用整轮并与其他并行 agent 争用同一集群/静态站，主动终止 |
| `pytest tests/kube-frontend -m ui -q -p no:cacheprovider -n 4`（全站并发） | 56% 时已出现大量失败（`F` 成片，含 `E` 错误），**与串行结果矛盾**，终止 |
| `pytest tests/kube-frontend/configmaps -m ui -q -n 0`（并发失败模块的串行复核） | **24 passed / 2 skipped**（77.21s），跳过原因：不足两页 / 没有超长键名的 ConfigMap |
| `pytest tests/kube-frontend/monitoring tests/kube-frontend/app-store -m ui -q -n 0`（本轮改动最多的两个模块串行复核） | **33 passed**（234.72s） |

## 3. 结论

- **并发（`-n 4`）在当前环境不可作为判定**：同一批用例并发跑大面积失败、串行跑全绿。原因是共享集群状态（列表总数、首页排序、`tc-e2e-*` 残留）与多个并行 agent 同时读写同一 B200 集群和同一份 `dist`，不是产品缺陷。这与迁移指南「串行仍是判定基准」一致，也印证了「并发失败必须串行确认」。
- **全站串行可行但需要专用窗口**：376 个文件 × 每个用例重新加载一次单页应用，实测约 100 分钟；期间不能被其他 agent 的构建、清理或数据写入打断。本轮不具备该窗口，故不宣称全站通过。
- **本轮及前几批的模块在合并后仍全绿**：monitoring 15 + app-store 18 = 33 passed；configmaps 24 passed。加上各批次自己记录过的串行结果（devops 12、镜像构建器 12、灰度发布 8、联邦 8、监控 5、成员 6、网关 5），本会话交付的页面族**在各自范围内均有串行证据**。

## 4. 未完成项与建议

- 全站串行 E2E 仍未执行完整一遍：建议在一个独占窗口（无并行 agent、无构建）执行 `pytest tests/kube-frontend -m ui -q -p no:cacheprovider -n 0`，并把结果写回本记录。
- 全站并发跑若要用，需要先做到：测试数据全部唯一前缀且清理、列表类用例不依赖全局总数、静态站使用同一份固定构建。
- 部署环境（B200 生产前端）与 member 集群的验收仍未执行，与本记录无关但同属 CHECK-02 的退出条件。
