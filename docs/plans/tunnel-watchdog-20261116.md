# 隧道看门狗：挂死的转发要能被发现（2026-11-16）

> 新增 `tests/ui/tools/tunnel-watchdog.mjs` + `tunnel-watchdog.test.mjs`（3 条自检）。

## 1. 与隧道代理的分工

上一轮加了 `tunnel-proxy`，解决的是「ssh 退出后 1 秒的重连空窗」。本轮遇到的是**另一种故障**：

| 故障 | 表现 | 谁负责 |
| --- | --- | --- |
| ssh 退出 | 端口没人听，连接被拒（ECONNREFUSED） | 重连循环 + 代理 |
| **ssh 还活着但转发挂了** | 端口在听、连接被接受，**但永远没有响应** | **看门狗（本轮）** |

实测证据（本轮开场）：`curl` 通过隧道 8s 返回 `000`，而 `ssh sgb000 'echo ok'` 仍然正常。
**TCP 层探测会认为它是健康的**，所以探针必须是带超时的 HTTP 请求。

## 2. 做法

每 15s 对隧道发一次带 8s 超时的 HTTP 请求；连续 2 次失败就执行重启命令
（`pkill -f "ssh -N -L 18089"`，重连循环随即把它拉起来）。成功即清零计数。

实测恢复：杀掉挂死的 ssh 后，**4 秒内**隧道恢复 `200`。

## 3. 自检 3 条（`node --test`）

| 断言 | 内容 |
| --- | --- |
| 健康时不重启 | 隧道正常应答 → 绝不执行重启命令 |
| **挂死时重启** | 上游接受连接但从不响应 → 2 次探测失败后执行重启 |
| 有恢复日志 | 启动时打印监视目标，成功时不误判 |

**实测 3 passed。**

## 4. 一次几乎误判的负向验证（重要教训）

为了证明「自检真的会失败」，我把 `probe()` 改成永远 `return true` 再跑测试。前三次结果都是 **3 passed**，
我一度准备在记录里写「这些自检不敏感」。

第四次我把**篡改后的代码打印出来**，才发现前三次的篡改**根本没生效**（heredoc 静默失败），文件一直是原版。
用 Node 直接改写后再跑：

```
not ok 2 - restarts a tunnel that accepts connections but never answers
```

**自检是敏感的，是我的验证手段在骗我。**

固化下来的做法：负向验证必须**先证明篡改已生效**（打印被改的那段代码），再看测试结果。
否则「测试通过了」和「测试根本没跑」看起来一模一样。

## 5. 另一个真实的测试缺陷（本轮修掉）

自检原先用固定端口（19201/19211/19221），第二次运行时撞上上一轮遗留的服务：
`EADDRINUSE: 127.0.0.1:19211`——**测试因与看门狗无关的原因失败**。改为监听 0 端口（系统分配），不再冲突。
