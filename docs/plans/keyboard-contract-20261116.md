# 键盘与焦点契约（2026-11-16）

> 新增 `kube-frontend/config/keyboard-contract.test.ts`（3 条）。迁移的目的之一是**换掉手写交互、改用 ai-kit 原语**，
> 而原语的价值（焦点陷阱、Escape、tab 顺序、可访问名称）会被三种「抄近路」悄悄抵消，且都不是类型错误。

## 1. 三条断言

| 断言 | 防的问题 |
| --- | --- |
| 不把 `onClick` 挂在 `div/span/li/td/tr` 上 | 只有鼠标能点，键盘用户不可达，读屏也不当作交互元素 |
| 不手写弹层 | `role="dialog"` 自绘 + 手写 Escape ⇒ 没有焦点陷阱、没有焦点归还，后续每个修复都要做两遍 |
| 每个按钮都有可访问名称 | 图标按钮被读成光秃秃的「按钮」 |

## 2. 一个真实的方法论坑（第一次写错）

首版用 `/<(div|span…)\b[^>]*?onClick/` 匹配，**负向验证时没能拦住**故意植入的 `<div onClick={() => undefined}>`——
因为 `[^>]*?` 在箭头函数的 `=>` 处就停了。

改为一个小状态机 `openingTag()`：从 `<div` 起逐字符扫描，跟踪 `{}` 深度与引号，只有在「括号外且不在字符串里」
遇到的 `>` 才算标签结束。改完再植入同样的违规 → **契约立即失败**；恢复后全绿。

> 结论：负向验证不是形式主义——如果只跑正向，这个契约会永远「通过」，包括在被破坏的时候。

## 5. 边界

契约是**静态检查**：它保证不出现已知的坏写法，不能证明 tab 顺序合理、焦点可见、读屏朗读顺序正确。
这些仍需浏览器实测（`Tab` 走查、焦点环截图），在 B200 链路可用时补。
