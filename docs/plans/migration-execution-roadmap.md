## 边界与基线

- 真实环境使用 B200；本地全栈与部署环境分别验证，不能用前者代替后者。
- 老代码用于盘点行为和接口；新实现避免复制 AGPL 源码。目标仓库的许可证兼容性、
  依赖及历史代码的许可结论须由项目方审核，不能仅凭重新实现认定合规。
- `gap_check.py` 只按 URL 段检查归宿，**不能证明子页、权限或写能力已完成**。
  企业空间已有概览、项目、成员、配额、角色和用户组入口，不能算整块空白；
  集群快照列表和类型入口已存在，但快照内容及旧入口兼容性仍需核实。
- 已有页面保持可用；每轮先对照老页面与新实现，记录照搬、改进及不迁移，
  不把报告里的旧数量或模块菜单开关当作实时事实。

## 执行顺序

| 阶段 | 范围 | 开始前核实 | 完成条件 |
| --- | --- | --- | --- |
| 0 基线 | 修正清单误报，核对能力矩阵和现有未提交工作 | 路由、注册表、接口及现有测试 | 清单无未归类；差异与待办可追溯 |
| 1 运维闭环 | 容器日志与终端、负载详情、YAML 编辑 | 已实现的能力、权限和运行时行为 | 对照老功能逐项验收；未做项写明原因 |
| 2 日常资源 | 集群快照内容与旧入口、存储及 Service/Ingress 等创建能力 | API 资源版本、权限、旧路由语义 | 列表、详情和写入分别覆盖；写入测试回读并清理 |
| 3 通用体验 | 列表刷新、分页档位、空态出口及列显隐 | 各 API 分页模型，已用组件和业务需求 | 分页状态与服务端一致；共享组件和接入页均有测试 |
| 4 企业空间 | 角色、用户组、配额、成员授权和部门 | 真实 API、授权模型及现有六个入口 | 防止错误授权；列表与可用写操作完成验证 |
| 5 监控和集群能力 | GPU/应用监控、JuiceFS、集群网关 | API discovery、指标白名单、控制器状态 | 无数据与不可用区分；单位和接口来源可核对 |
| 6 其他作用域 | DevOps、联邦项目、商城缺失功能 | 实际服务与权限，不以菜单开关断言接口不存在 | 可用功能按独立范围迁移；不可用项保留探测证据 |

阶段是优先顺序，不代表整阶段必须一次交付；每次选择一个可验收的功能点。
项目级自制应用、节点 shell、kubectl、商城安装等仍需分别核验，不因相关页面存在而标记完成。

## 每轮交付

1. 对照旧路由与子页面、新实现及 B200 API；明确本轮范围、权限和未做项。
2. 按 SDD 同步 PRD、design、规格与一对一测试；跨页面能力记录契约与被否方案。
3. 独立实现、优先复用组件；共享组件变更补 Storybook 与单测。
4. 运行相关测试和 `python3 prd/tools/verify.py --no-e2e`；涉及 UI 的功能在本地全栈
   和 B200 实测，提交前串行 E2E。写入用例唯一命名、回读，并在失败时清理。
5. 更新能力矩阵及缺口登记，区分已验证、部分完成和环境阻塞；保留既有工作。
