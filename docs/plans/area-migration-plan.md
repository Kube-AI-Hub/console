## 1. 分区依据：老 console 的导航定义

> `config.yaml` 定义的是**菜单**：下钻页（容器详情、项目详情、网关详情、快照内容）、

按区域拆分后，改动一个区域只影响该区域的 HMR 图。

## 2. 结构约定（改不动的部分）

### 2.1 区域注册表是唯一声明处

`apps/console-next/src/areas/registry.ts` 同时驱动侧栏、区域页签、面包屑与路由可达性。
**新增页面必须在这里登记**，否则页面存在但侧栏到不了——已发生过一次（集群配置字典）。

### 2.2 每个页面一个文件夹、三个文件

```text
routes/<scope>/<page>/
  route.tsx    # 只渲染 <Outlet/> 的布局路由
  index.tsx    # 列表 / 主页面
  $name.tsx    # 详情（有详情时）
```

原因不是洁癖：文件式路由里 `<page>.tsx` 会成为 `<page>.$name.tsx` 的**父路由**，列表若忘了 `<Outlet/>`，
详情 URL 会渲染成列表（踩过一次）。三件套由 `config/area-contract.test.ts` 守住。

### 2.3 地址不加区域段

路径保持老 console 形状并加 `/kube-frontend/` 前缀，**不插入区域名**。区域只影响侧栏与页签。

### 2.4 页签切换不产生文档请求

区域内页签是真实 `<a href>`（可中键/⌘ 新开），普通点击走客户端跳转。

## 3. SDD 落地方式（每个功能点一次闭环）

```text
tree.py → build_prd.py → prd(AC) → design(承接 AC) → spec(covers/story) → 测试文件（路径镜像 spec） →
generate_case_docs.py → check_docs.py --strict → parity_check.py
```

硬要求：

1. 一 spec 一测试文件，路径镜像 `specs/`；一个文件一个测试函数，docstring 首行是字面 TC ID。
2. AC 只在**功能点文件**里声明一次；L2 索引重复声明会被门禁判为编号重复。
3. 设计文档「已知坑」必须写**不知道会怎样**，不是写「注意」；决策要带被否方案与何时重新考虑。
4. 文档里「明确不做」必须与实现同步——这项滞后过两次（存储扩容、用户创建已完成却仍列在「不做」）。

## 6. 已沉淀的决策与不变量

这些是**跨页面**的结论，来自踩过的坑，改动前先看这里。

### 6.1 数据读取

1. **写走原生组、读走 kapis**：kapis 的 `resources` 端点只注册 GET，写返回 405；个别对象写会 400 `wrong resource GroupVersionKind`。
2. **`metrics.k8s.io` 与 KubeSphere 监控不是一回事**：前者只给「当前用量」，后者才有总容量/已分配/配额/GPU。集群级用量读 KubeSphere named metrics；节点与项目的使用率读 `metrics.k8s.io`（B200 实测 200）。两者都不可用时显示 `-`，不显示 0。
3. **接口返回形状不统一**：`components` 返回裸数组，其余返回 `{items}`；读取端两种都接受。
4. **指标缺失 ≠ 指标为 0**：不返回该指标与返回空 result 都要渲染成「不可用」，不显示 0。
5. **Pod 指标结构与节点不同**：节点是 `{metadata, usage}`，Pod 是 `{metadata, containers:[{usage}]}`。
   「计数正确、测量值为 0」是这个错的特征。

### 6.2 写入语义

6. **JSON merge patch**：`null` 删除键、键缺失表示不变、空 map 什么都不做。
   清空一个注解必须显式发 `null`——这是本项目**第三次**踩到（配置字典别名、EditInfoDialog、集群描述）。
7. **PUT 是整对象替换**：只发部分字段会清掉其余字段（编辑配置字典数据时清空过创建者与别名注解）。
8. **改 IAM 用户角色用 PUT，PATCH 返回 405**；IAM 对不存在的用户返回 **500**（消息含 `not found`），需窄条件判定。
9. **企业空间的正确写路径是 kapis**：`/kapis/tenant.kubesphere.io/v1alpha2/workspaces`（POST 200），
   `/apis/tenant...` 是 404；PATCH 返回 500，编辑用 PUT。
10. **平台角色必须写原生 RBAC**：走 IAM 创建返回 200 但 `rules` 被丢弃；`apiGroups` 留空必须写成 `[""]`。
11. **告警的资源名随版本变**：3.3 是 `alertingrules`，3.4 是 `rulegroups/globalrulegroups/clusterrulegroups`。
    读不存在的资源会得到 200 空体，看起来像「模块未安装」——用 API 组的 `resources` 清单探测，不要用版本号猜。
12. **百分比型指标必须除以总量**：`cluster_cpu_usage` 单位是核、`cluster_memory_usage_wo_cache` 是字节。
    直接当百分比会得到荒谬值（实测 937053405184%）；CPU 更隐蔽——512 核集群里 34 核画成 34% 看起来完全正常。
13. **上游错误正文经常是纯文本**：admission webhook 用纯文本说明原因，BFF 若只读 JSON 的 `message` 就会把它替换成
    `Conflict`。非 JSON 且非 HTML 的正文必须保留。

### 6.3 呈现

11. **不显示与事实不符的 0**：指标未到时是「未知」/「计算中」，不是 0；「0 / 0」读起来像功能坏了。
12. **颜色不是唯一信息通道**：能力徽标只渲染支持项，不给「不支持」染灰色——实测全部渲染会被读成「都支持」。
13. **状态文案收敛到一处**：`lib/status.ts` 的 `statusLabel` 是唯一映射，未知值原样返回（不猜）。
14. **空值统一 `-`，时间统一 `formatTimestamp`**。
15. **行操作标签是静态的**：需要随行变化的标签，用两个互斥 `visible` 的菜单项，不要让标签说谎。
16. **能点就不能无效**：不支持的操作用 `visible` 隐藏，而不是点了静默 return。

### 6.4 表单与弹窗

17. **字段键不能带点**：`setByPath` 会把 `requests.cpu` 当嵌套路径（配额编辑踩过），用 `requests_cpu` 再映射回来。
18. **提交失败必须在对话框内显示**：`ResourceForm` 曾直接 `await onSubmit()`，失败变成 unhandled rejection，界面毫无反应。
19. **校验失败把焦点移到第一个错误字段**，否则用户在折叠线以下看不到错误。
20. **先开弹窗再加载数据**，加载中要显示 loading（用户要求）。

### 6.5 测试

21. **断言不要写死实现细节**：精确集合断言被新增列打破过 4 次，改为子序列断言。
22. **「只验证按钮可用」不算验证功能**：批量删除曾因此长期不可用（要求逐字输入全部名称拼接）。
23. **用例必须回读数据**：页面显示成功不等于保存成功（merge patch 类缺陷只看界面发现不了）。
24. **慢不是跳过的理由**：慢查询要在用例里重试，而不是报「无数据」。
25. **大批量同时失败先查端口**：静态服务进程退出与产品故障表现一致（根因已修，见 §8.2）。
26. **对象名不要按时间取模**：`int(time.time()*1000) % 1_000_000` 每 1000 秒循环一次，
    一次失败留下残留对象后，之后每次运行都 409，表现成「创建对话框不关闭」。用 uuid。
27. **用例不要选别的用例创建的对象**：`tc-e2e-` 前缀的对象随时会被所属用例删除，
    用它做断言目标会得到「行不见了」而不是「那不是我的对象」。
28. **表单挂载晚于弹窗**：弹窗出现后立即填表会让字段留空、下一次点击落在动画中的遮罩上；
    先等字段可见再填。

### 8.3 三个来自实测的设计决定

1. **GPU 按卡计数，不按百分比**。B200 有 15 张卡、已分配 6 张、利用率 26%。「6 / 15」直接回答
   「还能不能再起一个 GPU 任务」，「40%」不能——而且「已分配满、利用率低」正是需要被看见的组合。
2. **两个数据源独立降级**。集群对象是静态事实（版本、就绪、模块），监控是测量值。合成一个查询会让
   「没装监控」这种常见部署形态变成整页失败。实测两个接口都可能单独缺失或单独可用（首次探测 B200 的 metrics 报 404，复测为 200，说明这类结论必须复测）——
   反过来也成立。
3. **模块列表读 `status.configz`，未知键原样显示**。该集群实测含 `dongba`、`platformModel`、
   `network.ippool` 等非标准键。按老 console 的六个固定图标渲染会低报已装模块；按白名单过滤同样会漏。

### 8.4 两个必须避开的读取陷阱

- **`scheduler_schedule_attempts` 是按 result 标签分多条序列**（`scheduled` / `unschedulable`）。
  只取第一条会把两个语义完全不同的数混成一个。
- **指标缺失 ≠ 指标为 0**。监控 API 对不存在的指标不返回该 `metric_name`，对存在但无数据的返回空
  `result`。两者都必须渲染成「不可用」而不是 0%，否则「没装监控」会被读成「集群完全空闲」。

### 8.5 顺带修掉一个让整轮测试崩掉的真缺陷

本轮重建前端时 5178 的静态服务进程**退出**了，直接导致上一轮「20 个用例同时失败」。根因在
`kube-frontend/scripts/dev-static-server.mjs`：

```js
} catch {
  const shell = await readFile(join(distDir, 'index.html'));  // ← 没有二次保护
}
```

`vite build` 会清空并重写 `dist/`，中间有一瞬间连 `index.html` 都不存在。这个 reject 逃出
请求处理器 → 未处理的 Promise 拒绝 → 进程退出。**端口消失的表现与产品故障完全一致**，这是它被
误判为代码问题两次的原因。

修复：外壳读取加二次保护，输出 `503 + Retry-After: 1`（「服务正常，产物正在替换」比死掉更准确）。
实测：构建窗口内返回 503，窗口结束自动恢复 200，进程不再退出。

**教训**：大批量同时失败时，先 `curl` 端口，再怀疑代码。

### 10.2 筛选控件没有稳定句柄（产品缺陷）

项目筛选是 Radix 的 select trigger，role 为 `combobox`；它只有 `aria-label`，**没有 `data-ai-id`**。
用例按 `get_by_role("button", name="全部项目")` 找它，每次都等满 30 秒——这不是用例写错，而是
**控件本身没有可寻址句柄**，与本仓库「所有交互元素可寻址」的约定不符。

修复：`ListFilter` 增加 `aiId`，`Select` 原语支持 `data-ai-id`（三个渲染分支都传），9 个列表页各自传
`<page>:filter:project`。用例改按句柄定位后 **3.2 秒通过**。

### 10.3 跨项目列表的行键用了 name，导致句柄重复（产品缺陷）

集群配置字典列表跨全部项目，行键却取 `name`。`kube-root-ca.crt` 在多个项目同名，于是：

- 复选框句柄渲染成 `cluster-configmaps:select:<name>`，**多条重复**；
- 选中状态也按 name 归档，跨项目会互相干扰。

`data-ai-row` 一直是 `namespace/name`，所以只有句柄暴露了这个问题。改为 `rowKey: row => `${row.namespace}/${row.name}``，
实测句柄变为 `select:default/<name>`，重复数 **0**。

1. **忽略唯一前缀**：`seeded_configmaps` 会给名字加 `pw<6位>` 前缀，fixture 却用传入的名字去找行。

1. **百分比必须相除**：`cluster_cpu_usage` 单位是核、`cluster_memory_usage_wo_cache` 是字节。

**（1）BFF 丢掉了上游的具体错误信息。** IAM 创建用户重复邮件时返回**纯文本**：

非 JSON 一律回落到 HTTP 状态文本，于是界面上显示 **`Conflict`**——读者无法知道该改什么。
已改为：非 JSON 且不是 HTML 时，取正文前 300 字符作为消息。

### 15.2 两个真实缺陷

**（1）脚手架会静默破坏 `tree.py`。** `add_feature.py` 用「从 `"id": "<子模块>"` 起数括号」定位子模块块结尾，

定义到了就报 `ready`，而实例仍在加载——此时表格是空的，读者与自动化都会把它读成「没有实例」。
改为两份都就绪才算 `ready`。用例随后通过（此前失败于「实例行数 0 与接口 1 不一致」）。

## 38. 第 106 轮：迁移页面对照报告（2026-11-14，B200）

### 38.1 为什么要有一个可判定的对照报告

目标是「逐页对比原页面与迁移页面的布局、字段、交互、功能」。此前这件事散落在每一轮的记录里：谁都能说「迁移了」，但**没有人能一眼看出每页到底覆盖了哪些字段、哪些交互、哪些是故意没做**。

本轮把它变成一份生成物：`docs/plans/page-parity-report.md`，**73 个页面、11 个功能模块**，每行三列——页面 / 验收场景（AC 编号，就是字段与交互的逐条断言）/ 有意未迁移（从 PRD「明确不做」小节汇出，理由写在 design 里）。

### 38.2 报告里的人工部分：跨页面差异

生成物只能覆盖「有什么」，覆盖不了「为什么和老的看起来不一样」。所以报告开头保留一张人手维护的差异表：

| 差异 | 原因 |
| --- | --- |
| 列表是页面、切换/编辑是弹窗 | 老 console 两者都有；页面负责浏览检索，弹窗负责单一动作 |
| 破坏性/可逆操作确认方式不同 | 按后果分级：移除集群输入名称，停止调度一次点击 |
| 同一对象只有一处编辑入口 | 两个入口冲突时无法判断以谁为准 |
| 接口不可用显示「不可用」而非空表 | 空表会被读成「没有」 |
| 明确不做而非放死按钮 | 死按钮承诺了做不到的事 |

### 38.3 生成过程中修掉的三处文档债

生成器照出 PRD 与实现已经不一致的地方：

1. `users.md` 的「明确不做」还写着「停用/启用用户（平台侧接口未验证）」——**已经做完并在用**（USERS-05）。

3. `user-detail.md` 说停用/删除「另立功能点」——实际已在列表行操作里。

## 41. 第 109 轮：把「并发抖动」与「真回归」分开（2026-11-14，B200）

### 41.1 问题

最近几轮的全量 E2E 里，每隔一两轮就会出现 1–3 条失败，单独复跑全部通过。原因是**同一集群上 4 个 worker + 静态服务器 + 另一条并行线**在抢资源：

- 列表页读超时（30s 预算被吃满）
- 静态服务器代理 `POST /api/session/login` 偶发 502 或挂 20s+（直连 BFF 8092 一秒内返回 200）

这两种都不是产品回归，但都会让门禁变红。红得太随意，下一次真回归就不会有人当回事。

### 41.2 两处改动

| 位置 | 改动 |
| --- | --- |
| `prd/tools/verify.py` | E2E 失败后用 JUnit 报告取失败用例，**串行重跑一次**；一次失败+重跑通过 = 并发抖动（打印清单，不判失败）；重跑仍失败 = 真回归（判失败） |
| `tests/ui/conftest.py` | 登录取 token 失败时**重试 3 次（带退避）**；代理 502/超时不再让整套用例报「登录失败」，那与页面无关 |

### 41.3 关键设计：抖动要可见，不能被掩盖

重跑通过时必须**打印出被重跑的用例名**，并且仍计入本轮耗时。否则「自动重试」会变成把偶发 bug 藏起来。

### 41.4 验证

| 项 | 结果 |
| --- | --- |
| JUnit 解析器 | 自带 `_self_test_failing_node_ids()`（failure/error/pass 各一条） |
| 重跑分支 | 用桩 `subprocess.run` 走通：第一次失败并写报告 → 第二次按 node id 串行重跑 → 通过并打印 |
| 真实 E2E | 跑出 3 条失败，重跑仍失败——**这是真的环境问题**（同一时段代理登录出现 502/超时），直连 BFF 复查确认 |
| 登录重试 | 改动后随即跑 2 条用例：**9.89 秒通过**（此前同样时段会因登录 502 报错） |

### 41.5 结论

「重跑一次」不能修复环境，但能把**噪音从回归里摘出来**：现在红就是红，绿也说明了是怎么绿的。

## 48. 第 115 轮：密码强度条与特殊字符（推翻上一轮的两条判断）（2026-11-14，B200）

### 48.1 推翻的是我自己上一轮写的「明确不做」

上一轮我把老 console 的 `PASSWORD_DESC`（要求特殊字符）与强度条一起判成「不迁移」，理由写在 PRD 与
design 里：「文案要求特殊字符，但 `PATTERN_PASSWORD` 与服务端 admission 都不要求——文案在说谎」。
用户否了：**为了密码安全性，虽然后端不要求，但前端要校验**。

我的理由错在把「服务端不强制」读成了「不该强制」。这两件事不同：服务端不强制，等于**没有任何地方强制**，
而界面已经把这条承诺摆在那里。要么改文案，要么让文案成真——用户选后者。按迁移指导的三分类，这属于
**应当改进**，我上一轮误判成了**不该迁移**。

**被否方案（保留理由，供下一个人判断）**：改文案、去掉特殊字符要求，让界面与服务端一致。这条路仍然成立
且更省事，它只在「平台愿意接受更弱的密码」这个前提下才更好——本轮的前提相反。

### 48.2 最终规则（前端强制，两处共用）

| 项 | 值 |
| --- | --- |
| 长度 | ≥8 个字符，且 ≤64 字节（下限按字符、上限按字节，两个单位各守一端） |
| 小写 / 大写 / 数字 | 各至少一个（服务端也要求） |
| 特殊字符 | 至少一个，集合逐字沿用老 `PASSWORD_DESC`：`~!@#$%^&*()-_=+\|[{}];:'",<.>/?` 与空格（**服务端不要求**） |

文案即规则：`userSettings.password.rule` 就是老 `PASSWORD_DESC` 的迁移版，前半句逐字保留，只在长度那句补上字节上限。

### 48.3 强度面板：同一功能，换一种呈现

| | 老 console | 现在 |
| --- | --- | --- |
| 位置 | 输入框上方的浮层下拉，聚焦弹出、失焦消失 | 新密码框下方的**常驻内联面板** |
| 内容 | 「您的密码必须：」+ 三条 checklist + 进度条 + 一句提醒 | 同样四条 checklist（多一条「特殊字符」）+ 三档进度条 + 提醒 |
| 档位 | 分数 <6 红 33% / 6–8 黄 66% / ≥8 绿 100%，只有颜色 | 弱/中/强，**颜色之外必须有文字标签**（只靠颜色对色盲不可用） |

判定：**违反任一规则 → 弱**；规则全满足且 ≥12 个字符 → 强；否则中。所以「弱」的含义是「还过不了校验」，

## 56. 复盘：为什么验证和迁移慢，以及如何优化

先取证据而不是凭感觉。关键测量：

| 项目 | A100 | B200 |
| --- | --- | --- |
| 跨项目 ConfigMap 列表 | **25.4s** | **0.66s** |
| 持久卷列表 | 24s | 0.38s |
| pod metrics | 25s | 0.44s |

**结论一：慢的不是接口。** B200 上所有查询都在 0.5 秒内，A100 是它的 30–90 倍。之前大量
「等待放宽 / 重试 / 超时」的补丁都是在给 A100 的慢接口打补丁，问题本身不在代码。

| 项目 | 数值 |
| --- | --- |
| 145 个用例串行 | **14 分 33 秒** |
| 用例内固定 `wait_for_timeout` | 195 处，合计仅 **1.5 分钟** |
| 单用例平均 | **5.4 秒** |

**结论二：成本是「每个用例重新打开一次单页应用」的固定开销**（建页 ~1.5s + 冷加载 SPA ~2.5s +
真实交互 ~1.5s），不是等待某个具体响应。

**结论三：慢 → 不敢常跑 → 只在最后跑 → 一次暴露多个问题 → 反复返工。** 这是「迁移慢」的真正链路，
不是写代码慢。多数返工都发生在用例的精确断言与并发/时序上。

### 42.1 优化 1：并发执行（14 分 33 秒 → 3 分 48 秒，3.8 倍）

`pytest -n 4`。并发的前提是用例之间不共享可变对象，为此修掉三类真实缺陷：

| 缺陷 | 现象 | 修复 |
| --- | --- | --- |
| 固定对象名 | 7 个用例都创建 `case-a`/`case-b`，并发时互相删除 | 夹具按实例加唯一前缀 `pw<6位>` |
| 夹具参数名不实 | `annotations=` 被直接并进 `metadata`，别名注解根本没写进去 | 正确嵌套到 `metadata.annotations` |
| 依赖「第一行」 | 并发时那一行随时被别的 worker 删掉 | 自己创建、按名搜索后再操作 |

顺带清掉 A100 专属假设（硬编码项目 `kube-frontend-demo`）：改成运行时选取真实项目/自建对象。

### 42.2 优化 2：以 B200 为参考环境

A100 缺 `kube-frontend-demo`、指标接口 20 秒起、告警模块未装；同一套用例在 A100 上大量超时，
失败信息与产品无关。`.env` 已切到 B200（`KA_APP_URL=http://localhost:5178`，密码为 B200 admin）。

指标接口偶发不可用时，节点/项目用量列降级为 `-`，用例如实跳过并说明；不再因为环境缺资源而

### 50.21 减少轮数：把机械环节交给工具

统计 churn：`locales/src/index.ts` 21 次、`tree.py` 15 次、`catalog.yaml` 15 次、`api-client/src/index.ts` 13 次。
这些都是**每加一个页面就要手工改一遍的登记点**，改错一次就是一轮门禁往返。

#### 新增 1：`prd/tools/add_feature.py`（脚手架，一条命令生成六处登记）

原来新增一页要在六处手工登记，漏一处门禁就报错。现在一条命令生成：PRD 树节点、需求文档、
技术方案、用例规格、测试骨架、区域注册表条目。

实测：生成的骨架**直接通过文档门禁（0 错 0 警）**，不需要再补登记。

它只做机械部分，**不写页面、不猜字段、不填技术方案内容**——那些才是迁移真正的工作。

#### 新增 2：`prd/tools/verify.py`（一条命令收尾）

原来收尾要分别跑文档门禁、一致性核对、架构契约、3 个包的单测、E2E，分五次手敲必然漏跑，
而漏掉的那项往往正是下一轮返工的原因（改了共享组件却没跑契约）。

实测：静态与单测 **69 秒**全跑完；加 E2E 用 4 worker 约 5 分钟。

#### 新增 3：`prd/tools/cleanup_test_objects.py`（清理测试残留）

发现 `default` 里积了 **46 个** 历次运行留下的 `tc-e2e-*` / `pw*` 对象（secrets 18、SA 26）。
用例都在 `finally` 里删，但进程被中断/超时/fixture 中途失败时删不掉。残留会让列表变长、出现分页、
「第一行」不再是目标对象——**后续用例开始莫名失败，看起来像产品坏了**。

工具默认 dry-run，`--apply` 才删，且只认窄前缀（不做「看起来像测试就删」的猜测）。
清理后再跑，失败用例明显减少。

#### 另一个干扰源：并行会话

本仓库同时有另一个会话在同一集群上跑测试。并发会话之间会互相删除/创建测试对象，
造成偶发失败。**这解释了相当一部分「查不出原因」的抖动**——后续应以串行为判定基准，
并发跑只看趋势。

#### 已加入的静态护栏（省掉的往返）

`config/consistency-contracts.test.ts` 覆盖「声明了但没兑现」的四类，**第一次运行就抓到** 3 个
从未被引用的详情页组件（700+ 行死代码）与 4 处样式漂移的 `Row` 副本。

### 50.22 又一例「看起来在验证，其实什么都没验」

`ACCESS_CONTROL_USERS_02` 里这段断言：

```python
dialog.get_by_role("button", name="确认").click()
ui.page.wait_for_timeout(500)
assert "8 位" in dialog.inner_text()
```

它想验证「短密码被拒绝」。但 **「至少 8 位，需同时包含字母与数字」是密码字段的静态提示**，
始终显示在对话框里——所以这条断言无论校验是否生效都会通过。实测确认：提示文本与提交结果无关。

改成读回数据：

| 断言 | 含义 |
| --- | --- |
| 对话框仍然打开 | 提交被拒 |
| 列表里查不到该用户 | 确实没有创建 |

顺带发现：`GET /users/<不存在>` 在这套部署上返回 **500 而不是 404**，所以「是否存在」必须从列表回答，
不能读状态码——否则断言的是 BFF 的错误映射，不是业务事实。

（该用例独立跑一直通过，串行全量里偶发失败，正是因为 `wait_for_timeout(500)` 后立刻断言，
负载高时对话框还没渲染完。）

### 50.23 第二轮优化：能力接线契约 + 弱断言扫描

#### 新增契约：声明的能力必须接上 handler

「声明了排序、却没有 `onSortChange`」这类问题在这轮迁移里出现四次（排序死、搜索死、分页死、
搜索键死）。原来只靠人肉发现，现在静态检查：

| 声明 | 必须接上 |
| --- | --- |
| `sortableKeys` | `onSortChange` |
| `search` | `onSearchChange` |
| `filters` | `onFiltersChange` |
| `selection` | `onSelectionChange` |
| 多页 `pagination` | `onPageChange` |

「多页」的判定：`pagination` 里 `pageSize` 不是 `Math.max(...)`（那是把全量塞进一页的单页列表）。

**契约本身也验证过会失败**：临时删掉 `ComponentsPage` 的 `onSearchChange`，契约立刻报出该文件；
恢复后通过。一个不会失败的检查等于没有检查。

顺带查出 4 个页面声明了 `pagination` 但无 `onPageChange`——核实后确认都是单页前端列表，
无翻页控件，属于正确实现。

#### 弱断言扫描：找出「永远不会失败」的断言

迁移中至少四处断言永远为真，长期给绿灯：

| 断言 | 为什么永远为真 |
| --- | --- |
| `"8 位" in dialog.inner_text()` | 是密码字段的静态提示，始终在屏上 |
| `"小写字母" in dialog.inner_text()` | 是名称字段的提示 |
| `"数量" in dialog.inner_text()` | 是字段标签 |

统一改成「对话框仍开着 + 读回数据」。例如配额用例现在读回 `requests.cpu` 确认没被写成 `abc`；
扩容用例读回存储容量确认仍是 `1Gi`。

新增 `prd/tools/check_weak_assertions.py`，识别三类：固定 sleep 后紧接断言、断言文案在对话框里、
只断言元素可见。已接入 `verify.py`（**只提示不阻断**——重试循环里的 sleep 是合理的）。

#### 固定 sleep 改条件等待

| 用例 | 原来 | 现在 |
| --- | --- | --- |
| 平台角色翻页 | `sleep(2500)` 后读行 | 等「出现不同的非空行集」 |
| 存储卷排序 | `sleep(600)` 后读请求日志 | 等 `aria-sort` 到位再核对请求 |
| 表单焦点 | `sleep(500)` 后读 `activeElement` | `expect(...).to_be_focused()` |
| 批量删除 | `sleep(500)` 后断言按钮可用 | 直接 `to_be_enabled()`（本身会轮询） |

「等待不同的非空行集」这个细节值得记：一开始写成「等旧的第一行消失」，但加载时表格显示骨架行，
「消失」瞬间为真，断言随后读到空页——**等一个条件，要确保这个条件只在真正完成时才成立**。

**验证**：契约 517 项全绿；静态与单测 57 秒；相关用例逐个通过。

### 50.24 并行稳定性：失败用例从 5 → 0

并发的最后几个抖动逐个定位，根因都是**用例对「页面上恰好有什么」做了假设**：

| 用例 | 根因 | 修复 |
| --- | --- | --- |
| `BULK_DELETE_01` | 新建两个对象后假设它们在首页；列表按创建时间倒序，其他 worker 的新对象会把它们挤下去 | 两个对象用**同一前缀**，搜索该前缀让两行确定可见 |
| `DETAIL_02` | 仍取「第一行」再打开详情 | 改为操作自建对象 |
| `SEARCH_01/02` | 共享 `search()` 只 sleep 400ms | 改为校验输入值真的落下 + 等待结果反映关键字 |

过程中我自己写的等待条件也犯了两次**同一类错误**，值得记下来：

1. 「等旧的第一行消失」——加载时表格显示骨架行，「消失」瞬间为真，随后读到空页。
2. `all(keyword in name for name in row_names())`——**`all([])` 是 `True`**，空行集立即通过。

**结论：等一个条件，要确保这个条件只在真正完成时才成立。** 空集、骨架态、过渡态都会让「显然成立」
提前发生。这比原来「睡 2 秒」更难写对，但只有它能真正消除抖动。

最终：`configmaps` 三次连跑全绿；全量 E2E **150 通过 / 3 跳过 / 0 失败**（3 分 48 秒）。

| kubeconfig | **必须 `btoa` 编码**后写入 `spec.connection.kubeconfig`；直接发 YAML 会创建一个永远连不上的集群（老 console 的 `safeBtoa` 就是为此） |
| 联邦 | `spec.joinFederation: true` |
| 校验 | 名称（小写/数字/连字符）与 kubeconfig（含 `apiVersion`、`clusters`、`server`）在**发请求前**拦下；不做 YAML 解析，只为拦住「粘错文档」 |

实测：通过界面导入后读回对象，`type=direct`、kubeconfig base64 可解、`joinFederation=true`，
列表立即出现该集群。

**走过的一个坑**：`primaryAction` 只带 `key`，点击经 `onAction` 回到页面；我第一版给它加了
`onClick`，**TypeScript 没报错但运行时不生效**——按钮点了没反应。这类「schema 形状不匹配却静默失败」
正是本轮之前加的「能力接线契约」想覆盖的方向。

**2. 集群详情页左侧栏显示集群级菜单**

原来 `/clusters/<id>/…` 的左侧栏仍是**项目区条目**，而集群页的导航在**页签条**里。
按老 console 改为：进入集群后，左侧栏即集群菜单（集群概览/节点/项目/系统组件/配置字典/存储类型/
持久卷/集群设置/集群监控/节点用量/自定义资源），当前页高亮。

同时**删掉了重复的页签条**——同一份 12 项目录在侧栏和页签各出现一次不是特性。集群布局路由因此
只剩 `<Outlet/>`。用例从「点页签」改为「点侧栏」，并断言高亮项。

**验证**：全量 E2E **153 通过 / 3 跳过 / 0 失败**（4 分 09 秒）；文档门禁 0 错；一致性核对仅剩
并行会话的 `logging`。

### 50.27 集群管理与切换：对齐老 console 的三个交互

#### 1) 添加集群支持两种连接方式

老 console 的 `cluster.add` 有两条路径（KubeKey 新建 / 导入），导入又分两种连接方式：

| 方式 | 对象形态 | 行为 |
| --- | --- | --- |
| 直接连接 `direct` | `spec.connection = {type: direct, kubeconfig: base64}` | 创建前调 `POST /kapis/cluster.kubesphere.io/v1alpha1/clusters/validation` 校验连通性 |
| 代理连接 `proxy` | `spec.connection = {type: proxy}`，**无 kubeconfig 键** | 不做校验；成员集群需部署 agent |

**校验顺序是重点**：老 console 先 `validate` 再 `create`。实测这个端点要求 base64（传原始 YAML 返回
`illegal base64 data`），且完整但不可达的 kubeconfig 会在 10 秒后返回连接错误——用例据此断言
「对话框保持打开 + 对象未被创建」，而不是期望它成功。

**环境限制**：本平台未部署 tower 代理组件，`clusters/<id>/agent/deployment` 返回
`cannot generate agent deployment yaml ... because tower...`。因此：
- proxy 模式仍可创建对象（`type=proxy`、无 kubeconfig），但会长期未就绪；
- 概览页显示接入面板并**据实说明**「本平台可能未部署代理组件」，而不是假装在加载。

#### 2) 集群列表支持编辑信息

行操作「编辑信息」改四项：别名（`kubesphere.io/alias-name`）、标签（`cluster.kubesphere.io/group`）、
供应商（`spec.provider`）、描述（`kubesphere.io/description`）；名称只读。

**清空必须发 `null`**：merge patch 里「键缺失 = 不修改」，这是本项目反复踩过的坑；用例专门测了
清空后注解键消失。列表名称列改为「别名优先、副行对象名」，与老 console 的 `showNameAndAlias` 一致。

顺带修了一个自己写错的定位：名称列一开始用 `td` 序号取，取到的是状态列；改用 `data-ai-id`。

#### 3) 集群切换 + 侧栏按作用域

**不把列表改成弹窗**——老 console 两者都有：列表承担增删改与深链接，切换器承担「已在集群里」的快速跳转。

| 路径 | 侧栏 |
| --- | --- |
| `/clusters/<id>/…` | 顶部**集群切换器** + 集群菜单 |
| `/clusters`、`/access/*`、`/settings/*` | 平台导航（集群管理/配置字典/访问控制/应用商店管理/平台设置） |
| 项目页 | 项目区（不变） |

切换器读 `configz.multicluster` 判断是否多集群；选择后跳到目标集群的 `overview`（与老 console 的
`enterCluster` 一致），并记住选择（`kube-frontend:last-cluster:<用户名>`），用于构造无集群段的链接。
单集群安装不显示切换入口，且 `/clusters` 直接进入该集群概览。

**踩到的一个坑**：`Menu` 只认 `activeKey`，给条目传 `checked` 不会产生 `aria-current`——平台导航
一开始完全没有高亮，改为把匹配项折进 `activeKey`。

**验证**：全量 E2E **156 通过 / 3 跳过 / 0 失败**（3 分 59 秒）；集群管理套件 20 通过；
架构契约 552；api-client 178；文档门禁 0 错。

### 50.28 导航层级：平台 / 企业空间 / 集群 / 项目

按「菜单与管辖范围一致」重排导航，并落地两个具体修正。

#### 具体修正

| 修正 | 说明 |
| --- | --- |
| 切换器加「集群管理」 | 弹窗左下角链接到 `/clusters`：切完集群之后最常问的下一句是「还有哪些集群、怎么加」 |
| 删除集群级配置字典 | 从**集群侧栏**与**顶部平台管理菜单**两处移除，并删除页面本体 |

**为什么连页面一起删**：只藏菜单会留下不可达的死代码（`parity_check` 还会把它算作已迁移，文档与用例要继续养着）。它的能力——跨项目看 ConfigMap——已经由项目页筛选的「全部项目」提供（实测选中后请求 `/configmaps`，无命名空间段）。删除范围：路由 3 个文件、页面、控制器 `scope` 分支、注册表项、菜单项、11 个用例、11 份规格、16 份 PRD/设计、`tree.py` 节点与一致性核对映射。

#### 工作台不再是占位页

原来根路由是「选择一个模块」的占位页，硬编码一条指向 `system-workspace/host/default` 的链接；而顶部「工作台」指向 `/kube-frontend/`——**该路径没有路由**，点击落到 Not Found（这是本轮实测发现的既存缺陷）。

现在：
- `/kube-frontend/` 是正式路由，渲染工作台；`/` 只做重定向。
- 工作台按集群分节，节内按企业空间列出项目（项目胶囊带集群+命名空间），点击进入该项目控制台。
- **只列归属企业空间的命名空间**：没有 `kubesphere.io/workspace` 标签的命名空间不是项目（否则工作台会列出 `kube-system` 这类普通命名空间）。

数据来源的取舍：项目取自**集群命名空间列表**（带企业空间标签），而不是 tenant 的 `/workspaces/<ws>/namespaces`——后者**不返回集群**，而进入项目必须知道集群。

#### 项目上下文栏升级为三级

`企业空间 · 集群 · 项目`，且项目下拉**按企业空间过滤**（修正跨租户）。

| 改动前 | 改动后 |
| --- | --- |
| 项目下拉 20 项（集群内全部命名空间，含其它企业空间与系统命名空间） | 10 项（当前企业空间的） |
| 企业空间只在 URL 里 | 显示为企业空间标签 |
| 集群只读文本 | 集群下拉，切换时保留页面段 |

**顺带省掉一个每页请求**：集群下拉最初在页面加载时就取集群列表，让每个项目页多一次往返（实测每页 3 个请求）。给 ai-kit 的 `Select` 加了 `onOpenChange`，改为**展开时**才加载，页面请求回到 2 个。

#### 顶部导航的结论

保持「平台管理 / 工作台 / 应用商店」三入口，与老 console 一致：企业空间与集群控制台是**下钻**进入（平台管理 → 集群列表 → 某集群；工作台 → 项目），不额外增加顶级入口；平台管理下拉里去掉配置字典。

**验证**：串行全量 **157 通过 / 3 跳过 / 0 失败**（14 分 47 秒）；架构契约 570；api-client 178；文档门禁 0 错；一致性核对 0。

**过程教训**：一次串行跑期间我同时执行了构建与单测，结果跑出 2 个假失败（单独跑都通过）。**判定用的串行跑必须独占机器**。

### 50.29 平台信息 + 邮件通知渠道 + 主题色调

老 console 的「平台设置」有两个页面：平台信息（只读）与通知管理（每渠道一页）。本轮把两者
迁到新 UI，并按要求在平台设置里加主题色调。

#### 邮件渠道：一个渠道是三个对象

平台把通知渠道拆成三份，页面必须一起写：

| 对象 | 内容 |
| --- | --- |
| `default-email-config`（Config） | 传输：SMTP 主机/端口/TLS/用户名/发件人；密码只保留对 Secret 的引用 |
| `global-email-receiver`（Receiver） | 收件人与启用开关 |
| `global-email-config-secret`（Secret） | SMTP 密码（base64） |

老 console 的保存顺序是 config → secret → receiver，本轮照搬：先写 Config，再写指向它的
Secret 与 Receiver，失败时不会留下「有收件人但没有传输配置」的半套。

#### 三个「看起来成功」的坑（都实测踩到了）

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 保存返回 **405** | 创建时 POST 到了**对象**端点（`/configs/<name>`），而创建要 POST 到**集合** | `upsert` 读后决定：不存在→POST 集合，存在→PUT 对象；Secret 同样修正 |
| 保存返回 400、等 10 秒 | 平台校验 webhook（`vconfig.notification.kubesphere.io` → `notification-manager-webhook:443`）不可达 | 页面显示服务端原因；用例识别该原因并**如实跳过** |
| 点「发送测试」HTTP 200 但没发出去 | `/verification` **HTTP 200 + body `Status: 400`** 表示失败 | 判据取 body 的 `Status`，不看状态码 |

#### 「是否已配置」原来的判据是错的

旧页面查 `kubesphere-monitoring-system` 里名为 `mails`/`slacks` 的 Secret 来判断渠道是否配置。
实测该命名空间下没有这些 Secret（通知对象在 notification API 里），所以现在改为按对象是否存在判断，
并去掉「渠道概览」——每个渠道页自己显示已配置/未配置。`/settings/notifications` 保留为**重定向**
到 `/settings/mail`，旧链接不会 404。

#### 外观：深浅色 + 色调

平台信息页新增「外观」分区：主题模式（深/浅）与色调（紫罗兰/品牌绿）。两套调色板与持久化
（`data-theme` / `data-accent` + `localStorage` + 首帧恢复）在 ai-kit 里已有，这里只做控制面。
**它是浏览器偏好，不写任何平台对象**——放在平台设置是按要求的位置，设计里写明了这一点。

两个实现细节：图标集没有 sun/moon，按钮用文字标签；绿色调色板的强调色是 **mint**（`--ai-raw-mint-400`），
不是 `green-300`。

| 项 | 结果 |
| --- | --- |

## 57. 复盘：为什么会漏掉 115 个页面，以及从此如何避免

> 事实源：[new-ui-gap-analysis.md](./new-ui-gap-analysis.md)（老源码逐页对照，基线 `abea36211`）。
> 本节回答两个问题：**为什么每次报告都显示 0 缺口，却缺了大半**；**规则怎么改才不会再漏**。

### 58.1 结论先说：不是判断错了，是没进过清单

缺口分析里的 115 个页面，绝大多数**从来没被任何一次讨论否决过**。它们不是"考虑过、决定不做"，
而是**从未出现在清单里**——所以既没有文档、也没有 `status: 'planned'` 的登记、更没有用例。
`parity_check.py` 报 0、`check_docs.py` 报 0、计划报「页面已做完」，三个绿灯同时成立，
因为它们回答的是**别的问题**：

| 检查 | 实际回答的问题 | 被误读成 |
| --- | --- | --- |
| `check_docs.py` | 文档规格测试是否自洽 | 功能是否齐全 |
| `parity_check.py` | 已登记的页面是否都有规格 | 老页面是否都迁了 |
| `check_weak_assertions.py` | 断言是否可疑 | 覆盖是否充分 |

**没有一项检查在问「老 console 有多少页面、各去哪了」。** 这是整件事的根。

### 58.2 五条根因（每条都能指到代码/文件）

#### R1 清单来源错了：用了导航，而不是源码

§1 开头写的是"分区依据：老 console 的导航定义（`server/config.yaml`）……这是唯一权威依据"。
导航是**菜单**，不是页面全集。它至少漏三类：

| 漏掉的类别 | 例子 | 后果 |
| --- | --- | --- |
| 下钻页 | 容器详情 `pods/:pod/containers/:name`、项目详情、网关详情、快照内容 | 整页从未被枚举 |
| 详情页内的页签 | 老详情页是"左栏 + 页签"，页签本身就是独立页面 | 页签体系整体丢失（F-05~F-10） |
| 模块门控的菜单 | `enableAppStore` 为假时菜单不渲染 | 应用商店连"不存在"都没登记 |

迁移指南 §2.1 要求"以源码为准"，我们用在了**实现**阶段（读 `containers/**` 写页面），
但**没有用在清点阶段**——清点用的是导航。这一条贯穿了全部五条根因。

#### R2 检查粒度错了：一级目录 ≠ 一个页面，分组目录整块隐身

`parity_check.py` 按 `clusters/containers` 与 `projects/containers` 的**一级目录名**匹配。
老 console 恰好把页面按功能分组存放：

```text
clusters/containers/Workload/{Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, Pods, Services, Routes}  ← 8 页
clusters/containers/Storage/{Volumes, StorageClasses, VolumeSnapshots, VolumeSnapshotClasses, JuiceFS, PV}   ← 6 页
```

于是出现两种隐身：

| 隐身方式 | 机制 | 被吞掉的页面 | 现状（2026-11-14） |
| --- | --- | --- | --- |
| **被当作结构性目录** | `Workload` 在检查的 `STRUCTURAL_DIRS` 里 | 集群级应用负载 **8 页** | **已补齐**（缺口分析指出后当日迁入 `cluster-management`，`gap_check.py` 记为已迁移） |
| **整块算作一个已迁页面** | `Storage` 对上 `storageclasses` 就算迁移完成 | 集群级 PVC、快照三件套、JuiceFS **5 页** | 仍缺（§57.3） |

这个闭环本身就是最好的证据：**同一批页面，在清单里当天就迁完，不在清单里就一直没人发现。**

这不是"漏了一条规则"，是**度量单位选错了**：页面身份是 URL 路径，不是容器目录层级。
`gap_check.py` 因此改为按 `routes/*.js` 的 `path:` 枚举段（§57.4 M1）。

#### R3 术语混用：「作用域错误」被当成了「不做」

集群级配置字典/保密字典/服务账户被登记为"作用域错误——项目资源只在项目作用域看"。
这个判断对**那三个**资源成立。但它没被区分成

- **不是页面**（同一批对象，换个作用域看）→ 归 `ELSEWHERE`
- **决定不做**（做了也没用/环境不支持）→ 归 `UNMIGRATED` 并附探测证据
- **还没做**（承认，排期）→ 归 `PLANNED`

三者混在同一张"未迁移"表里，结果是：一条"作用域错误"的记录让整张表看起来已经处理过，
而同一批**集群级负载**（有真实差异：PROJECT 列、全命名空间筛选、集群角色权限口径）
也跟着一起被"算了"。

**规则**：一个页面只有三种归宿，各要有各的证据。**分不清是哪一种，就说明还没判定**（§57.4 M2）。

#### R4 「已迁移」只核页面在不在，不核能力够不够

`registry.ts` 的 `status: 'ready'` 只说明"这个路由有页面"。它不说：

| 维度 | 老 console | 新 UI | 差 |
| --- | --- | --- | --- |
| 可编辑 YAML 的资源 | 21 类 | 13 类 | −8 |
| 定制编辑表单 | 21 种 | 9 种 | −12（Deployment 只剩副本数） |
| 详情页页签 | 统一"左栏 + 页签" | 单页纵向分区，所有负载共用一个组件 | 全部 |
| 列表能力 | 每页档位、列显隐、刷新、实时 watch、空态出口 | 固定 10 条、无刷新、无实时、空态无出口 | 6 项 |

所以"页面 ✅"与"功能对齐"是两件事，而只有前者被度量过。
**Deployment 在计划里是 ✅，但它改不了镜像**——这是最典型的"看起来完成"。

#### R5 文档自己会漂移，而报告是从文档生成的

`page-parity-report.md` 由 `prd/tools/build_prd.py` 从 PRD 的「明确不做」小节生成。
PRD 不随迭代更新「明确不做」，报告就开始两头错：

| # | 报告/计划写的 | 代码实际 |
| --- | --- | --- |
| D-01 | 用户/企业空间编辑、平台角色创建是"另立功能点" | **都已实现** |
| D-02 | 项目成员邀请/改角色是"有意未迁移" | **已实现** |
| D-03 | 计划 §4.2 节点详情含"容器组"页签 | **没有**（parity 登记为有意不迁移）|

D-03 已在本轮修正（§4.2）。教训：**"明确不做"是代码状态的派生，必须与代码同步**，
否则报告既不能证明做了、也不能证明没做，只能证明"曾经写过一句什么"（§57.4 M4）。

#### 附：缺口为什么"看起来很小"

三个放大效应让缺口长期不可见：

1. **按作用域平均**：项目作用域 36 → 35 页，看起来几乎对齐，掩盖了集群作用域 54 → 24（其中 8 页是缺口分析指出后才补的）；
2. **"有替代"被当成"已迁移"**：改名（`volumes`→`persistentvolumeclaims`）与合并（网关详情变成只读卡片）
   都算过线，但前者等价、后者不等价；
3. **模块关闭提供了万能理由**：`openpitrix=false`、`devops=false`、`servicemesh=false` 都是事实，
   但它们只能解释那三块，不能解释集群级负载、快照、GPU、终端。

### 58.3 已登记缺口（14 项，持续可见）

`gap_check.py` 的输出即权威清单（跑一遍就能复现）。**登记口径只收"页面级"缺口**——
功能级（详情页签、编辑能力、列表通用能力）用能力矩阵（M3）承载，理由见 §57.6。

| 层 | 缺口 | 为什么难 |
| --- | --- | --- |
| **架构级**（4 项能力，无对应页面段） | 容器 exec / kubectl / 节点 shell / 日志 tail | 新 UI 无 WebSocket 通道；BFF 需支持 `upgrade`，不是"补一个页面" |
| **整块作用域**（1） | 企业空间控制台 18 路由 | 需要成员/角色/用户组一整套；Phase 2 |
| **集群作用域**（12） | 集群级 PVC、快照 4（快照/类型/内容/别名）、JuiceFS、GPU 2、应用资源监控、集群告警 2 | 页面本体多可复用，缺路由 + 侧栏登记 + 集群角色权限口径 |
| **平台设置**（1） | 飞书渠道 | 其余五种渠道已迁，字段结构同源 |

已完成的对照：集群级应用负载 8 页**已于本轮补齐**（缺口分析指出后当日完成），
这正是"登记 → 排期 → 落地 → 清单自动反映"应有的速度。

**优先级**（按"用户在运维里做不到什么"，不按"缺了几页"）：

| 优先 | 项 | 理由 |
| --- | --- | --- |
| P0 | 终端 / kubectl / 节点 shell / 日志 tail | 排障基本不可用；KubeSphere 最高频动作。**独立立项**，工作量与补页面不在一个量级 |
| P0 | 顶栏 2 个死链 + 无 404 兜底 | 成本极小，违反本计划自己定的"不做死按钮" |
| P1 | 详情页签体系、容器详情页、编辑 YAML 覆盖 21→13 | 编辑能力退化最伤日常（§57.2 R4） |
| P1 | 集群级 PVC / 快照 / JuiceFS | 存储运维在集群视角看不到全貌 |
| P2 | GPU 2 页、应用资源监控、集群告警 2 页、飞书渠道、列表通用能力 | 成体系补齐 |

### 57.4 从此如何避免：五条硬规则

#### M1 页面清单只能由脚本从源码枚举，不能来自导航

`prd/tools/gap_check.py` 按 `src/pages/*/routes/*.js` 的 `path:` 递归取段。
**新增一个老页面时，只要它在路由里出现，就必然进清单**——这是唯一不会漏的枚举方式。

#### M2 每一段必须落在四类之一，且各自要证据

| 类别 | 判据 | 证据要求 |
| --- | --- | --- |
| `✓ 已迁移` | 新 UI 有对应段 | 自动比对；改名登记在 `RENAME` |
| `⊘ 明确不做` | 决定不做 | **必须写原因**，且能追到 §5 的探测命令与返回 |
| `⇄ 别处承接` | 另一作用域/页面承接 | 写清在哪 |
| `… 已登记缺口` | 承认没做、有计划 | 指向本节条目 |

四类之外 = **未归类**，`gap_check.py --strict` 退出码 1，`verify.py` 直接失败。
**这条规则的意义不是让清单变空，而是让"没做"和"不做"分开。** 分不清的条目，就是下一个隐身缺口。

#### M3 「已迁移」必须同时登记能力覆盖度，不能只标 ✅

每个页面的状态从 `✅` 改为**能力矩阵**，至少四列：

| 列 | 含义 | 取值 |
| --- | --- | --- |
| 列表 | 列表页本身 | ✅ / 部分 / ✗ |
| 写 | 创建、编辑信息、编辑 YAML、删除 | 具体列到操作 |
| 详情 | 详情页与页签 | 页签列表，或"单页" |
| 通用 | 每页档位、刷新、实时、空态出口 | 逐项 |

**任何一列写"部分"的，必须在 `page-parity-report.md` 里有对应理由**，否则算未登记缺口。
§4.4 的"21 项写能力"从此按矩阵统计，不再用总数（总数掩盖了 21 类 → 13 类的退化）。

#### M4 「明确不做」与代码同源，且可反向核对

`page-parity-report.md` 从 PRD 的「明确不做」生成 → PRD 必须与代码同步。落地方式：

1. 每轮收尾跑 `build_prd.py` 重新生成报告，**diff 里出现"新增/删除明确不做"必须人工确认**；
2. `parity_check.py` 的 `UNMIGRATED`/`ELSEWHERE` 表就是"明确不做"的机器可读版本，
   `gap_check.py` 复用它——**同一事实只写一处**；
3. 反向核对：**已登记"不做"但代码里其实做了**（D-01/D-02）同样算文档缺陷，要删掉登记。

#### M5 每轮先回答"这一轮没做什么"

§7 的门禁原来只查"做完的有没有错"。从本轮起，每轮收尾必须贴一次 `gap_check.py` 的输出摘要：

```text
已迁移 43 / 明确不做 13 / 别处承接 5 / 已登记缺口 22 / 未归类 0
```

**数字比上轮大（未归类 ≠ 0）就要当场解释**。这一行写进每轮的"验证"小节，
缺口就不可能只存在于某一份分析文档里。

### 57.5 每轮必做清单（贴在 §7 之后执行）

```text
□ python3 prd/tools/gap_check.py --strict        # 未归类必须为 0
□ 若本轮新增了"不做"：原因能追到探测证据吗？写进 §5 了吗？
□ 若本轮迁移了一页：能力矩阵（M3）四列填了吗？"部分"有理由吗？
□ 若本轮改了"明确不做"：build_prd.py 的报告 diff 看过了吗？
□ 收尾贴出 gap_check 的汇总行，并与上轮比较
```

### 57.6 本轮自我检查：这份复盘有没有犯同样的错

| 复盘里的判断 | 证据 | 会不会漂移 |
| --- | --- | --- |
| 老 console 200 条路由 / 181 页面单位 | 缺口分析 §9.2 的可复现脚本 | 脚本在文档里，可随时重跑 |
| 115 真缺失 / 22 有替代 / 31 疑似回归 | 缺口分析 §3–§5 逐条带 `路径:行号` | 每条可指到源码行 |
| 14 个已登记缺口 | `gap_check.py` 的输出（机器可复现） | 工具跑一遍就有 |
| `Workload` 被结构性跳过 | `parity_check.py` 的 `STRUCTURAL_DIRS` 含 `'Workload'` | 代码即可验证 |
| `Storage` 整块算一页 | `CLUSTER_PAGES["storage"] = "storageclasses"` | 代码即可验证 |

**刻意没做的一件事**：没有把 115 个缺口全部塞进 `PLANNED`。只登记了 14 项
"看得见、可排期"的**页面级**缺口；详情页签、编辑能力、列表通用能力这些**功能级**缺口
用能力矩阵（§57.4 M3）承载——**两类缺口混在一张表里，清单会失去可执行性**，
而清单一旦没人看，就又会退化回"不可见"。

**另一个自我检查**：本节写下的每条根因都带代码位置。如果哪天有人把
`gap_check.py` 删了或绕过它，§57.4 M2 的"未归类必须为 0"就立刻失效——
所以它接在 `verify.py` 里，是门禁的一部分，不是文档里的一句建议。
