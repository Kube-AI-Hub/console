# 隧道代理：把「一秒的重连空窗」变成「稍慢的请求」（2026-11-16）

> 新增 `tests/ui/tools/tunnel-proxy.mjs` + `tunnel-proxy.test.mjs`（4 条自检）。

## 1. 问题

B200 的 SSH 隧道每隔几分钟断一次。`ssh -L` 大约 1 秒就能重连，但**那一秒里本地端口没人监听**，
于是这期间每一个连接都被拒绝，BFF 把它报成：

```
502 upstream_unreachable  connect ECONNREFUSED 127.0.0.1:18088
```

**一秒的隧道抖动 → 一个看起来像产品缺陷的失败用例。**前几轮反复出现的 502 就是这么来的。

## 2. 做法

在隧道前面放一个**永不关闭监听**的 TCP 代理：

```
BFF ──► 127.0.0.1:18088 (node 代理，始终在听)
                     └─► 127.0.0.1:18089 (ssh -L，断了就重连)
```

上游不可达时，代理**在内部重试**（默认 250ms 间隔、20s 预算），而不是拒绝客户端。
20s 预算用尽才真的失败——那时确实是隧道长时间不可用。

## 3. 实测（真实栈）

| 动作 | 结果 |
| --- | --- |
| 正常请求 | `200`（2.6s） |
| **`kill -9` 掉 ssh 监听**（模拟隧道掉线），立即请求 | **`200`（21.0s）** —— 不是 502 |
| 之后再次请求 | `200`（3.8s） |

改造前同样场景是 `502 ECONNREFUSED`。**这是本轮最硬的证据。**

## 4. 自检 4 条（`node --test`）

1. 上游在时正常转发；
2. **上游短暂消失时，客户端连接仍被保住**，上游回来后照常拿到应答；
3. 上游一直不回来 → 预算耗尽后失败（不无限挂起）；
4. **4MB 响应体完整送达**（不截断）。

**实测 4 passed。**

## 5. 一次诚实的自我修正

我一度怀疑「上游 close 时 destroy 客户端」导致了大响应截断，并删掉了那两个 handler、加了第 4 条自检。
但**把 handler 加回去，第 4 条自检并不失败**——说明 Node 在 `close` 前已经把数据刷完，
我**无法证明**那是截断原因。

因此记录里明确写：handler 被移除是因为「上游关闭就销毁对端」原则上就是错的，
**不是**因为有测试证明了它导致截断。删掉它是简化，不是修 bug。

## 6. 仍未解决

`CLUSTER_CONFIG_01` 在代理生效后仍以 `IncompleteRead(153558)` 失败（两次重试都截断）。
这与此前记录的 454KB / 768KB / 8.4MB 是同一类现象，**不能归因于代理**——代理的自检证明它能完整转发 4MB。
该用例的结论仍待链路能稳定承载该响应。
