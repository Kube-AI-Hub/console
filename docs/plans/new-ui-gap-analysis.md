## 1. 判据：什么叫「迁移完成」

按[迁移指南](../legacy-ui-migration-guide.md) §1 与[单页模板](page-migration-template.md) §6，**完成是多维判定**，不是「有路由」：

| 维度 | 判据 | 谁证明 |
| --- | --- | --- |
| 旧能力覆盖 | 未映射能力数 = 0，未证明的承接数 = 0 | 单页交付记录里的原子能力表 |
| 数据语义 | 请求 → 映射 → 展示三段对账，单位/标签/精度 | 同次响应对账断言 |
| 交互与权限 | 动作实际走通、写入回读、作用域隔离 | E2E + 非 admin 实测 |
| 视觉与主题 | 逐页签新旧对照、三档截图、计算色 | 人工复核 + 令牌契约 |
| 验证与部署 | 本批串行 E2E、全站回归、部署环境 | 各自独立结论，不得合并 |

**三层判据各管一段**，不能互相顶替：

| 层 | 工具 | 能证明 | **不能**证明 |
| --- | --- | --- | --- |
| 页面段 | `gap_check.py` | 每个老 URL 段有归宿 | 页内能力、页签、字段 |
| 原子能力 | 能力矩阵 §0 台账 | 某个能力做到哪一步、证据在哪 | 部署上的真实表现 |
| 验收证据 | 各页交付记录 | 何时/在哪/什么构建上验过 | 换环境后仍然成立 |

> 迁移指南 §6 的原话：**不要把「新实现、新 PRD、新测试互相一致」误写成「与旧版完整一致」。**
> 本轮复验严格遵守这一条：下面的「已交付」一律指**有实现代码**，不等于已验收。

## 3. 腿二：独立实现（AGPL → Apache）→ 无残留

这是本次任务措辞里最容易被忽略、但法律上最硬的一条：**新 UI 必须是独立实现，不能是 AGPL 代码的搬运。**

### 3.1 结论

**新 UI 侧没有任何 AGPL 残留**，且有一处**主动替换 AGPL 依赖**的证据。

| 检查 | 结果 | 证据 |
| --- | --- | --- |
| 新 UI 许可证 | **Apache-2.0** | `kube-frontend/LICENSE`、`apps/console-next/package.json`、`packages/*/package.json`、`packages/ai-kit/package.json` 全部 `"license": "Apache-2.0"` |
| 旧 console 许可证 | AGPL-3.0 | `console/LICENSE` 为 GNU Affero GPL v3；`console/package.json` 为 `AGPL-3.0` |
| 新 UI 源码里的 AGPL 文件头 | **0 处**（仅 2 处**注释**提到 AGPL） | `grep -rln 'GNU Affero\|AGPL' apps packages server` |
| 对旧 AGPL 组件库的依赖 | **0 处** | 无 `kube-design` / `@kube-design/` 出现在 `apps/console-next/package.json` 与 `packages/*/package.json` |
| 对旧 `console/src` 的引用 | **0 处** | `grep -rn "from 'console/src" --include=*.ts --include=*.tsx` 无命中 |

### 3.2 两处「提到 AGPL」的注释是**独立性证据**，不是污染

| 文件 | 内容 | 说明 |
| --- | --- | --- |
| `apps/console-next/src/lib/base64.ts:1-12` | 说明老 console 用 `js-base64`（**AGPL-3.0**）规避 `btoa` 的 U+00FF 限制，因此**在 `TextEncoder`/`TextDecoder` 上重写**同等行为 | 主动绕开 AGPL 依赖的典型做法 |
| `apps/console-next/test/resource-lib.test.ts` | 同一段说明的测试侧引用 | — |

### 3.3 技术栈差异本身就是独立实现的证据

| 层 | 旧 console（AGPL） | 新 UI（Apache-2.0） |
| --- | --- | --- |
| 框架 | React 18 + mobx + 类组件 | **React 19 + TanStack Router/Query + 函数组件** |
| 样式 | SCSS + `kube-design` 组件 | **Tailwind 4 + 自研 ai-kit** |
| 列表 | `withList` HOC + `Table` | **schema 化 `ResourceList`（列是数据）** |
| 状态 | mobx store | React Query |
| 服务端 | Node 中间层 | **无独立服务端**（ks-console 托管 + ks-apiserver 直连） |

两套栈没有可复用代码，新实现只能照着**行为**重写——这正是迁移指南 §11 的要求
（「旧组件源码只作清点与行为契约参考，仍需独立实现 Apache 代码」）。

### 3.4 边界：这一节能证明什么、不能证明什么

- **能证明**：新 UI 仓库里没有 AGPL 文件、没有 AGPL 依赖、没有跨仓库 import。
- **不能证明**：逐行「独立创作」的合规结论。执行路线已写明：**「目标仓库的许可证兼容性、依赖及历史代码的许可结论须由项目方审核，不能仅凭重新实现认定合规。」**
  本节是**技术侧证据**，法律结论需项目方出具。

1. **功能覆盖与独立实现两条腿已经站住**：`gap_check` 未归类 0，Apache-2.0 无 AGPL 残留。这两条不需要再论证，只需要防止回退——现有的 20 个架构契约就是防回退的那一层。
2. **唯一实质差距是验收**，且**卡在一件小事上**：mlu370 的账号密码。拿到之后按[执行路线](migration-execution-roadmap.md)的顺序跑：
   `--keyboard-local` → `--locale-scan` → 整轮基线，作为**新架构的第一次验收**。
3. **验收前不要宣称「全部完成」**。指南 §10 要求四种结论分开报告：本地该页通过 / 全仓静态通过 / 全站 E2E 通过 / 新版生产·member 验收。当前只有前两种普遍成立。
4. **台账要顺手修两处漂移**：CHECK-09 仍把第三方登录/账单写成「待重纳实现」（实为已交付）；`gap_check.py` 的 `SCOPE_DIRS` 仍缺 `console` 与 `terminal`（10 条全局路由不在 93 里）。
