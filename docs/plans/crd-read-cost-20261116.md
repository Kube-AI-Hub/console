# `CUSTOM_RESOURCES_01` 的读取开销修正（2026-11-16）

## 1. 之前为什么总是失败

用例为了核对「页面是否真的用 `limit=-1` 展示全部行」，原来自己先把**整份 CRD 列表**读一遍再比行数。
在本集群这是一次数 MB 的 chunked 传输，实测：

| 轮次 | 现象 |
| --- | --- |
| 15:50 | `IncompleteRead(8416130 bytes)` |
| 17:00 | `IncompleteRead(454438 bytes)` |
| 18:04 | 外层 380s 超时（读不完） |

## 2. 修正：用一次小请求拿总数

实测 `GET …/customresourcedefinitions?limit=1` **1.2 秒**返回，带
`metadata.remainingItemCount = 234`（总共 235 个 CRD）。于是：

- `_crd_sample(api, 20)`：`?limit=20` 取样本，用于挑一个「有 kind 和 scope」的目标；
- `_crd_total(api)`：`?limit=1` + `remainingItemCount + len(items)` 得到总数；
- 断言仍是「页面行数 == 总数」——**含义不变**，但读取开销从数 MB 降到 1.2 秒的几 KB。

## 3. 修正后的实测

用例总耗时从「>380s 超时」降到 **67.93s**，但仍以
`IncompleteRead(768206 bytes)` 失败——这一次卡在**页面自己**加载 CRD 列表（数 MB），
与用例的读取无关，属于链路对大响应体的截断。

## 4. 结论

用例的**读取侧**问题已经解决（快了三个数量级）。剩下的失败是环境限制：
这条链路无法稳定传输 MB 级响应体，而「自定义资源」页面的数据本身就是这么大。
该用例的最终结论要等链路能承载大响应，或等集群 CRD 数量下降。

已记录的三次截断点（454KB / 768KB / 8.4MB）足以说明这不是偶发。
