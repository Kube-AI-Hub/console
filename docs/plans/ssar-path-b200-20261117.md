# 权限检查的 iam 路径在两个环境上都 500（2026-11-17）

## 现象

B200 八段式基线出现 **9 + 14 条失败请求**（页面本身仍渲染，0 error）：

```
500 /kube-frontend/kapis/iam.kubesphere.io/v1alpha2/selfsubjectaccessreviews
```

## 直接探测（`--probes`，只读）

```
                  A100            B200
workspaces        200             200
ssar-native       201             201
ssar-iam          500             500      ← 两个环境都一样
configz           200             200
monitoring-nodes  200             200
alerting          200             200
events-v1         200             200
```

## 结论

- **`/kapis/iam.kubesphere.io/v1alpha2/selfsubjectaccessreviews` 在两个部署上都不可用**
  （`no matches for iam.kubesphere.io/v1alpha2, Resource=selfsubjectaccessreviews`）；
- 原生 `/apis/authorization.k8s.io/v1/selfsubjectaccessreviews` 两个环境都返回 **201**；
- 这条 iam 路径的改动目前在 `permissions.ts` 的工作区改动里（未提交），因此 B200 基线会红。

## 一处需要更正的判断

本文第一版写着「A100 上 iam 路径可用」，依据是「A100 基线 0 失败请求」。**那是错的**——
基线绿灯只能说明**当时**没有页面走这条路径，不能说明这个接口可用。
`--probes` 直接打接口才看清：两个环境都是 500。

> 规则：**接口可用性要直接探测，不能从「页面没报错」反推。**

## 更正二：这不是缺陷，是「探测 + 回退」

`permissions.ts` 里已经写了回退：IAM 路由缺失（404/405/或 500 且报 `no matches for iam.kubesphere.io`）时，
改用原生 `authorization.k8s.io/v1`。所以页面**功能正常**，只是每次都会先发一条注定 500 的探测请求。

因此巡检把这一条 500 归入「预期内的失败」（与成员集群的 `resourcequotas` 404 同类），不再计入 `failed requests`。
判定有单元测试（`tools/test_multicluster_retries.py`，含「同一路径上的 403 不算预期」）。

## 建议

若想消掉这条噪声，可以让权限检查直接走原生路径；否则保留探测 + 回退也能工作。
